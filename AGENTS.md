# Project architecture

- Agenda submenu visibility and page access share the URL-to-menu-slug catalog; the Agenda parent gates its Outlet to prevent mounting unauthorized pages. These UI checks do not replace server authentication or data access policies.
- Sector group menu choices derive from the shared catalog sections (`menuSectionOf`, mirroring the sidebar groups incl. "Aplicações" and its Agenda submenu), so new submenus can be configured consistently.- CRM tabs come from `CRM_TABS` in `src/lib/crm-tabs.ts` (menu slugs `crm.<key>`); the CRM menu item exists only when a tab is allowed, and the server checks the same rule via SQL `crm_tab_allowed(<key>)` (RLS on CRM tasks/flows, guards in CRM server fns), so new tabs appear in sector-group settings automatically. Tables shared with Chat/Relatórios are not tab-gated by RLS.
- Email polling links replies to existing tickets (protocol in subject/body → Office 365 conversation → normalized subject) and stores them as `email_reply` comments with a pending flag instead of opening new tickets; matching rules live in `src/lib/email-thread.ts` with tests, so threading stays testable without the mailbox.
- Ticket auto-assignment RPCs must join `profiles.user_id` (auth id), not `profiles.id`, because `service_tickets.assigned_to` and `user_sector_assignments.user_id` store auth user ids.

- Assistente IA attachments live in the shared `ai_assistant_files` catalog (private bucket `ai-attachments`); messages reference files via `attachment_ids`, and catalog matching rules live in `src/lib/ai-file-match.ts` with tests, so file lookup stays testable.
- Estoque kits/acessórios and the link/unlink audit live only in our DB (`accessory_catalog`, `equipment_kit_items`, `gsystem_vinculos_historico`); kit changes go through the `set_equipment_kit_item` RPC and plate links through `vincularPlaca` server fn so saldo and history stay consistent. KPI rules live in `src/lib/estoque-kpis.ts` with tests.
- Assistente IA behavior settings (tone, format, creativity, forbidden topics, fallback, automations) live as columns on the single `ai_assistant_config` row; prompt rules are built by `src/lib/ai-guidelines.ts` and the `ai-assistant` edge function keeps a byte-identical copy between `// >>> guidelines` markers (a test enforces it) because Deno cannot import from `src/`.
- CRM client proposals are frozen snapshots in `crm_proposal_links` opened at public `/proposta/$token`; the random token is the only credential, so public server fns return only that link's data; items/values are released only by the CPF unlock server fn (the GET returns branding/status only), and accept/reject stage rules live in `src/lib/crm-proposal.ts` with tests. Branding/templates come from the single `crm_proposal_settings` row (Configurações > CRM).
- Configurable tables (column picker, Excel-style header filters, .xlsx export) use `src/components/data-table/*` with pure rules in `src/lib/table-columns.ts` (tested); column visibility is saved per browser in localStorage, so reuse these instead of per-page filter code.
- Ticket categories come from our `ticket_categories` catalog (synced from GSystem every 30 min by `listTicketCategories`; local active/term settings survive sync); screens read it via `useTicketCategories` and send `gsystemKey` to GSystem, so category choice is ours, not GSystem's.
- Technical service terms (`technical_service_terms`, public `/termo-servico/$token`, CPF gate like proposals) gate scheduling via `assertSchedulingAllowed`/`markTermScheduled`; the technical protocol's stage lives only in `service_tickets.tech_stage` (set by term triggers), finalization goes only through a linked test (`tech_protocol_id` + `test_result`) or refusal close, managers override with a reason, and the 8h no-response notice is the SQL cron `termo-sem-resposta-8h`; rules live in `src/lib/technical-terms.ts` and `src/lib/technical-service-cycle.ts` with tests.
- Gamification (ex-TOP Gamific) lives in `gamif_*` tables under `/gamificacao`; balances change only via entries trigger and security-definer RPCs (redeem, decide, link legacy user, duel respond/vote/resolve), processes version via `gamif_save_process`, and scheduled notices are delivered lazily by `gamif_dispatch_scheduled_notifications` when someone opens the area (no polling cron). `GAMIF_RELEASED` in `src/lib/gamif-rules.ts` gates collaborator screens (released to everyone; Admin tab stays admin/gestor); pure rules (streak, duel outcome, reading status, reports, settings) live there with tests.
- TOP Gamific import is closed: its DB functions and `/export` server fn were dropped at cutover, so nothing writes from TOP anymore; `gamif_import_runs` (last report) and `gamif_import_exclusions` stay as read-only history, and `src/lib/gamif-import.ts` keeps the tested mapping rules only for that report's types.
- Global polling intervals live in `src/lib/polling.ts` and the QueryClient pauses polling in background tabs; menu badges and the tab-title count come from the single `sidebar_counters` RPC (`useSidebarCounters`, refreshed by realtime events), so don't add per-badge polling or `auth.getUser()` calls in global components (use `useAuth`).
- The chat-list "who sent last" arrow reads `zapi_chats.last_message_from_me`, kept by an AFTER INSERT trigger on `zapi_messages`, so message writers need not set it and `listAllOpenChats` never reads messages.
- Technical log retention runs in the daily pg_cron job `retencao-logs-diaria` (SQL-only); audit_logs, zapi_messages and tickets are never purged by it.
- Acceptance terms live in the `technical_term_types` catalog (immutable `key`, stored in `technical_service_terms.term_type` and `ticket_categories.technical_term_type`; optional `default_service_type`, one per type), while `technical_service_terms.service_type` holds only the fixed service types from `FIXED_SERVICE_TYPES` (trigger-validated; legacy rows have service_type = term key); terms freeze `service_label`/`term_label`/title/text/checklist at creation and deletion goes through `delete_technical_term_type` (inactivates when used), so sent terms never change.
- Every RLS table in public (except profiles/user_roles) has a RESTRICTIVE "Only active staff" policy using `is_active_staff()`, and public signup is disabled (users created only by admin), so inactive or stray accounts read nothing; add the same policy to new tables.
- Financeiro (BPO) lives in `fin_*` tables under `/financeiro`; access is ONLY the `fin_acesso` allowlist via SQL `can_access_finance()` (RLS on every fin_* table and the private `fin-comprovantes` bucket, plus `assertFinance` in server fns and MCP tools), not the admin role nor sector menus. "Vencido" is computed on read; Drive receipts arrive through MCP tools `financeiro_*` (dedup by unique `drive_file_id`) and land as `revisado = false` for review; pure rules (DRE, cash flow, OFX/CSV, reconciliation, file-name hints) live in `src/lib/finance.ts` with tests. GSystem invoices (`/faturas/{cpfCnpj}`, per client) are imported as `receber` rows with `origem = 'gsystem'` and unique `gsystem_fatura_key`, in time-boxed batches whose resume point lives in `fin_gsystem_sync` (button in Contas a receber; pg_cron job `financeiro-faturas-gsystem` calls hook `/api/public/hooks/sync-gsystem-faturas` every 10 min with the `fin_cron_token` header, and the hook starts a new round at most hourly while finishing an unfinished round on every call); open invoices always, paid/cancelled only for the last 12 months, and a payment set in the Financeiro is never reopened by the sync; mapping rules live in `src/lib/finance-gsystem.ts` with tests.
- CRM Pós-venda (tab `posvenda`) works on `crm_posvenda_carteira` (all GSystem PJ clients plus paying PF; revenue = 3-month average of GSystem invoices in the Financeiro, ABC class by cumulative revenue, rebuilt by `atualizarCarteiraPosVenda` via service role at the end of each invoice round or by button, never touching contact/diagnosis fields) and `crm_posvenda_contatos` (each contact; an AFTER INSERT trigger updates last/next contact, NPS, sentiment and diagnosis on the client). RLS is `crm_tab_allowed('posvenda')`, so the post-sale user needs no Financeiro access; cadence (A 15, B 30, C 90 days), health/risk, suggestions, metrics and contact scripts live in `src/lib/posvenda.ts` with tests.
- Reconnect (ex-Reconnect Hub, `/reconnect`) lives in `rc_*` tables (same columns and ids as the old project, so the JSON backup import in Configurações is an idempotent upsert by id); access is `reconnect_allowed()` (admin/gestor or sector menu `reconnect`). Spreadsheet import rules (same-day accumulation, recovered detection on the first import of the day, skipped rows, discard filter) live in `src/lib/reconnect.ts` with tests; xlsx is vendored in `src/vendor/xlsx`. Notifications go out by `enviarNotificacaoReconnect`: WhatsApp through a Central Z-API channel and e-mail through an `email_channels` box (both chosen in `rc_settings`); clients link to `companies` by normalized name. Offline plates feed the Pós-venda risk: `sincronizarRiscoReconnect` (service role, after each Reconnect import and at the end of `atualizarCarteiraPosVenda`) links Reconnect clients to `crm_posvenda_carteira` by company CNPJ then company-name key and writes `rc_placas_paradas/rc_dias_max/rc_notificadas`, which `saudeCliente` discounts; the Resultados tab (`resultadoReconnect`) returns revenue figures only to admin, Financeiro or Pós-venda users. Linking and metrics rules live in `src/lib/reconnect.ts` with tests.
- Contratos (menu `/contratos`, slug `contratos`, server/RLS gate `contratos_allowed()`: admin/gestor or a sector group that explicitly lists the menu; it is not in DEFAULT_OPERATOR_MENUS) keep editable templates in `contratos_modelos` (seeded on first use from `src/lib/contratos-modelos.ts`, converted from the company's Word files with `{{campo}}` blanks) and drafts in `contratos.dados`. Sending freezes `conteudo_html` + SHA-256 and only server fns (service role) may change a sent contract (trigger `contratos_protege_enviado`). The public `/contrato/$token` page releases the text only after the signer's CPF and signs with a 6-digit code sent by WhatsApp/e-mail whose hash lives in server-only `contratos_codigos`; every step lands in `contratos_eventos` (audit trail). CONTRATADA and up to two witnesses sign as logged-in users. Alternatively a draft goes to Autentique (`provedor = 'autentique'`; key/sandbox/webhook secret come from env AUTENTIQUE_* first, else from server-only `integracoes_segredos` saved by admins in Configurações › Integrações via `salvarConfigAutentique`, read by `configAutentique()` with a 60 s cache; the status card only needs admin/gestor, not the Contratos tables): a PDF is generated from the frozen text with pdf-lib (`contrato-pdf.server.ts`), the signer gets Autentique's link and the sender signs as CONTRATADA by account e-mail; webhook `/api/public/hooks/autentique` never trusts the body and only re-reads the document from the API (`sincronizarAutentique`) (event parsing in `documentoDoWebhook`, tested, accepts both documented payload shapes; the document query inlines the id instead of a typed variable; a contractor rejection cancels the contract; "Sincronizar pendentes" re-reads every `enviado` contract in ~20 s rounds for when the webhook is missing; the account import also runs in ~20 s rounds resumed by page; the webhook URL shown always uses the public production host), and such contracts are blocked from the own-signature flow. Configurações › Integrações shows the Autentique status card (`integracaoAutentique`: key, account/credits, sandbox, webhook URL) and imports existing account documents as contracts with `dados.importado = true` (no frozen text; client and validity can be completed via `ajustarContratoImportado`, dedup by `provedor_documento_id`). Admin/gestor always see the Contratos page; when `contratos_allowed` errors (migrations not applied) the page shows the server error instead of 'acesso restrito'. The list supports multi-select bulk actions (`src/components/contratos/acoes-lote.tsx`): resend for signature (`reenviarContratosLote`, mode Autentique `resendSignatures` or the signer link — Autentique `createLinkToSignature` or our own — sent through the Central WhatsApp/e-mail box), category `categoria` cliente/fornecedor (`categorizarContratos`) and folders `pasta` (`moverContratosPasta`, which also moves Autentique documents to a same-name Autentique folder, created when missing, tracking `provedor_pasta_id`); columns from migration 0061, and the list query falls back to the old columns when it is not applied. Rules (fields, qualification, rendering, validity/renewal status, masks) live in `src/lib/contratos.ts` with tests. Automatic rules are configured in Configurações › Contratos (single row `contratos_config`, migration 0062): signature reminders by days since sending (`lembretes_enviados` counts the step even on failure), validity-end notices per threshold (`avisos_enviados` keys `venc:<fim>:<dias>`), annual adjustment by IPCA/IGP-M/INPC 12-month accumulation fetched from the BCB SGS API or a fixed % (listed in Contratos › Reajustes, applied by `aplicarReajuste` into `valor_mensal_atual` + `reajustes` history, never automatically), a draft contract created once per accepted CRM proposal (`proposta_link_id` unique, hooked in `respondToProposal`), and the Financeiro check (contract value × carteira revenue for clients or 3-month paid average for suppliers, only for `can_access_finance` users). The daily routine `rotinaDiariaContratos` runs from pg_cron job `contratos-rotina-diaria` (08:20 SP) via hook `/api/public/hooks/contratos-diario` with the `contratos_cron_token` header; sending that works outside a request lives in `src/lib/contratos-envio.server.ts`. Bulk PDF download zips with vendored fflate (`src/vendor/fflate`). Pure rules live in `src/lib/contratos-automacao.ts` with tests.
