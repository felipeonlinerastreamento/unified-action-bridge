# Project architecture

- Agenda submenu visibility and page access share the URL-to-menu-slug catalog; the Agenda parent gates its Outlet to prevent mounting unauthorized pages. These UI checks do not replace server authentication or data access policies.
- Sector group menu choices derive from the shared catalog, with Agenda entries grouped separately, so new submenus can be configured consistently.- Email polling links replies to existing tickets (protocol in subject/body → Office 365 conversation → normalized subject) and stores them as `email_reply` comments with a pending flag instead of opening new tickets; matching rules live in `src/lib/email-thread.ts` with tests, so threading stays testable without the mailbox.
- Ticket auto-assignment RPCs must join `profiles.user_id` (auth id), not `profiles.id`, because `service_tickets.assigned_to` and `user_sector_assignments.user_id` store auth user ids.

- Assistente IA attachments live in the shared `ai_assistant_files` catalog (private bucket `ai-attachments`); messages reference files via `attachment_ids`, and catalog matching rules live in `src/lib/ai-file-match.ts` with tests, so file lookup stays testable.
- Estoque kits/acessórios and the link/unlink audit live only in our DB (`accessory_catalog`, `equipment_kit_items`, `gsystem_vinculos_historico`); kit changes go through the `set_equipment_kit_item` RPC and plate links through `vincularPlaca` server fn so saldo and history stay consistent. KPI rules live in `src/lib/estoque-kpis.ts` with tests.
- Assistente IA behavior settings (tone, format, creativity, forbidden topics, fallback, automations) live as columns on the single `ai_assistant_config` row; prompt rules are built by `src/lib/ai-guidelines.ts` and the `ai-assistant` edge function keeps a byte-identical copy between `// >>> guidelines` markers (a test enforces it) because Deno cannot import from `src/`.
- CRM client proposals are frozen snapshots in `crm_proposal_links` opened at public `/proposta/$token`; the random token is the only credential, so public server fns return only that link's data; items/values are released only by the CPF unlock server fn (the GET returns branding/status only), and accept/reject stage rules live in `src/lib/crm-proposal.ts` with tests. Branding/templates come from the single `crm_proposal_settings` row (Configurações > CRM).
- Configurable tables (column picker, Excel-style header filters, .xlsx export) use `src/components/data-table/*` with pure rules in `src/lib/table-columns.ts` (tested); column visibility is saved per browser in localStorage, so reuse these instead of per-page filter code.
- Ticket categories come from our `ticket_categories` catalog (synced from GSystem every 30 min by `listTicketCategories`; local active/term settings survive sync); screens read it via `useTicketCategories` and send `gsystemKey` to GSystem, so category choice is ours, not GSystem's.
- Technical service terms (`technical_service_terms`, public `/termo-servico/$token`, CPF gate like proposals) gate scheduling: Seu Instalador create fns call `assertSchedulingAllowed` and `markTermScheduled`, and a DB trigger blocks non-manager ticket finalization for term-requiring categories until a term is `enviada`; rules live in `src/lib/technical-terms.ts` with tests.
- Gamification (ex-TOP Gamific) lives in `gamif_*` tables under `/gamificacao`; balances change only via entries trigger and security-definer RPCs (redeem, decide, link legacy user), and `GAMIF_RELEASED` in `src/lib/gamif-rules.ts` keeps it admin-only until release, so production screens stay untouched.
